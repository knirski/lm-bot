## Implementation guidance — idiomatic direct-style FP

Read this before taking R1–R6. The findings are small individually, but most of them are the same
underlying shape: a fallible step written as a `try`/`catch` or a nested `match` because there is no
house idiom for "unwrap this `Either` or give up". Scala 3.8 has one, it needs no library, and it
fits Gears exactly — Gears is itself direct-style, so `Either` + a boundary is the whole story.

### G1 — The vocabulary, and what stays out

**In:** Gears `Async` as a capability in the signature; `Either[DomainError, A]` as the result;
closed error ADTs (`ApiError`, `LuxmedError`, `CryptoError`, `SessionStoreError` — all already
correct); `scala.util.boundary` for short-circuiting; opaque types and smart constructors at the
boundary; effects (`now`, `uuidGenerator`, transport) passed as parameters.

**Out, deliberately:** no `cats`/`ZIO`, no `EitherT` or any monad transformer, no `IO`/`Future`
wrapper, no `Try` in a signature, no `.get`/`.toOption.get` outside tests. Spec §5.7.1 already bans
`scala.concurrent` outside `frontend/.../bridge/`; the point of direct style is that there is nothing
to stack in the first place. If a fix seems to want a transformer, it wants a boundary.

The existing code is already close. `LuxmedClient` uses for-comprehensions where a chain is clean
(`passwordGrant`) and `match` where it must also mutate state (`persistSession`) — both fine. What
follows removes the remaining noise, which is concentrated in `AccountService` and
`AccountClientFactory`.

### G2 — `result` + `?`: the direct-style bind

Two small definitions replace every nested `flatMap`/`match` ladder over `Either`:

```scala
package lmbot.backend.support

import scala.util.boundary
import scala.util.boundary.{Label, break}

/** Direct-style short-circuiting over `Either`.
  *
  * Inside a `result` block, `expr.?` yields the `Right` value or abandons the whole block with the
  * `Left`. This is the direct-style equivalent of a for-comprehension, without forcing every step
  * into a single chain.
  */
object result:
  inline def apply[E, A](inline body: Label[Either[E, A]] ?=> A): Either[E, A] =
    boundary(Right(body))

  extension [E, A](self: Either[E, A])
    /** Unwrap, or abandon the enclosing `result` block with this error. */
    def ?[B](using Label[Either[E, B]]): A = self match
      case Right(value) => value
      case Left(error)  => break(Left(error))
```

The free type parameter `B` on `?` is what makes it usable: the error type `E` must match the
enclosing block, but the value type does not, so a `Either[ApiError, Seq[Row]]` unwraps inside a
block returning `Either[ApiError, List[AccountView]]`.

Usage — note it reads top-to-bottom, and every line is an ordinary `val`:

```scala
import lmbot.backend.support.result
import lmbot.backend.support.result.?

def list(ownerId: Long): Either[ApiError, List[AccountView]] =
  result:
    val rows = attempt(dbFailure)(accounts.listOwned(ownerId)).?
    rows.toList.map(row => toView(row).?)
```

That replaces `AccountService.scala:119-134` — the `foldRight` over an
`Either[ApiError, List[AccountView]]` accumulator — with two lines that short-circuit on the first
bad row. `-Wunused:all` and `-Werror` are on, so add `import result.?` only in files that use it.

### G3 — `attempt`: one place where thrown failures become values

Foreign code throws: JDBC, JCA, `UUID.fromString`. Right now each site hand-rolls
`try … catch case _: Exception => Left(ApiError.Unexpected(…))`, which is why the same string appears
five times across `AccountService` and `AccountClientFactory`, and why `delete` (R3) could be missed.
One combinator fixes both:

```scala
package lmbot.backend.support

import scala.util.boundary
import scala.util.control.NonFatal

/** Runs a block that may throw at a foreign boundary (JDBC, JCA) and converts the failure into a
  * domain error. Never catches `Break` (which would silently discard `result` control flow) and
  * never catches `InterruptedException` (a cancellation signal, not a domain failure).
  */
object attempt:
  inline def apply[E, A](onFailure: Throwable => E)(inline block: => A): Either[E, A] =
    try Right(block)
    catch
      case escape: boundary.Break[?]       => throw escape
      case interrupt: InterruptedException => throw interrupt
      case NonFatal(error)                 => Left(onFailure(error))

  /** As `apply`, for a block that already returns `Either`. */
  inline def either[E, A](onFailure: Throwable => E)(
      inline block: => Either[E, A]
  ): Either[E, A] = apply(onFailure)(block).flatten
```

`R3` then becomes a single expression, and the fix cannot be forgotten at the next repository call
because the repository call site is where `attempt` lives:

```scala
def delete(ownerId: Long, accountId: AccountId): Either[ApiError, Unit] =
  attempt.either(_ => ApiError.Unexpected(accountDeleteFailed)):
    if accounts.deleteOwned(accountId, ownerId) then Right(()) else Left(ApiError.NotFound)
```

The `onFailure` parameter is where classification belongs, which turns R2's duplicated
`23505` handling into one named total function instead of two `catch` blocks at two nesting levels:

```scala
private def persistFailure(error: Throwable): ApiError =
  if hasSqlState(error, "23505") then ApiError.Conflict(duplicateLabel)
  else ApiError.Unexpected(linkFailed)
```

Note `NonFatal` rather than the current `case _: Exception`: `_: Exception` catches
`InterruptedException` and `Break` too, which is exactly the bug G4 describes.

### G4 — Three hazards when boundaries meet catch-all handlers (all verified)

1. **`boundary.Break` extends `java.lang.RuntimeException`.** A catch-all between the `break` and
   its boundary swallows it, and the block then returns a *fabricated success*. Verified — the same
   program with and without the rethrow:

   ```text
   unsafe (Break swallowed, real error lost): Right(-1)
   safe   (Break propagates to boundary):     Left(real error)
   ```

   This is not hypothetical for this codebase: `AccountService`, `AccountClientFactory`,
   `PostgresSessionStore` and `SessionCodec` all contain `catch case _: Exception` or
   `catch case _: Exception => …` handlers that sit exactly where a `?` would break through. Adopt
   `attempt` (G3) *before* introducing `?` into a method that still has a hand-written catch-all, or
   add `case escape: boundary.Break[?] => throw escape` as the first case of every catch-all you
   keep.

2. **Magnum's `transact` catches `Throwable`, rolls back, and rethrows** (verified from
   `magnum_3-1.3.1` bytecode: `Connection.rollback()` followed by `athrow` in a handler whose
   exception table entry is `java/lang/Throwable`). So a `?` that breaks out of a `transact` block
   rolls the transaction back and still delivers its `Left` to the boundary — correct for error
   paths, and worth knowing rather than discovering. The corollary: **never `break` with a success
   value out of a `transact` block**, because that rolls back the work you are returning. Put the
   boundary *outside* the transaction and keep the transaction body a plain computation.

3. **A `Label` must not outlive its boundary.** Never capture one in a lambda that runs later — a
   spawned Gears fiber, a `Future`, a callback. Breaking after the boundary has returned throws.
   Every use in this PR's code is a straight-line call stack, so this is a rule to write down, not a
   present problem.

### G5 — What R2 + R3 + R6 look like together

`link` currently nests: `validate(...).flatMap` → `try` → `match` on the auth result → duplicate
check → inner `try` → `catch` × 2 at two levels (`AccountService.scala:33-112`). In direct style the
control flow is flat and each line is one fallible step:

```scala
def link(ownerId: Long, request: LinkAccountRequest)(using Async): Either[ApiError, AccountView] =
  result:
    val normalized = NormalizedLink.from(request).?
    val existing = attempt(dbFailure)(accounts.listOwned(ownerId)).?
    Either
      .cond(
        !existing.exists(_.label == normalized.label),
        (),
        ApiError.Conflict(duplicateLabel)
      )
      .?
    val id = attempt(dbFailure)(accounts.reserveId()).?
    val deviceUuid = uuidGenerator()
    val session = clients
      .forLink(normalized.username, normalized.password, deviceUuid)
      .authenticate()
      .left
      .map(linkError)
      .?
    val stored = attempt(persistFailure)(accounts.insert(row(ownerId, id, deviceUuid, session, normalized))).?
    toView(stored).?
```

`Either.cond(test, (), error).?` is the idiomatic guard — it keeps the precondition an expression
rather than an `if`/`else` that has to carry the whole remaining body in its `else` branch. Reading
the block top-to-bottom now *is* the order of operations, which is what makes R2 obvious: the
duplicate check sits above the `authenticate()` line, and nothing else has to move.

### G6 — Short-circuit vs accumulate: pick deliberately

`?` short-circuits on the first error. That is right for `list` and `link`. It is *wrong* for
`Config.fromEnv`, which deliberately reports every bad env var at once — and the existing
`ListBuffer` there is the correct shape for that job, not something to "modernise". Direct style has
no `Validated`; when you want accumulation, say so explicitly:

```scala
val (failures, views) = rows.partitionMap(toView)
if failures.isEmpty then Right(views.toList) else Left(failures.head)
```

The rule of thumb: **accumulate at a configuration or form boundary where the user fixes all of them
at once; short-circuit everywhere else.**

### G7 — Narrow at the boundary, then pass the narrowed type

`validate` (`AccountService.scala:140-155`) returns `Either[ApiError, LinkAccountRequest]` — the same
type it was given. Nothing downstream can tell a validated request from a raw one, and the password
is still a bare `String` at that point. The project already does this properly for `Port` and
`AppVersion`; do it here too:

```scala
final case class NormalizedLink private (label: String, username: String, password: Secret)

object NormalizedLink:
  private def bounded(value: String, max: Int, required: String, tooLong: String): Either[ApiError, String] =
    val trimmed = value.trim
    if trimmed.isEmpty then Left(ApiError.Validation(required))
    else if trimmed.length > max then Left(ApiError.Validation(tooLong))
    else Right(trimmed)

  def from(request: LinkAccountRequest): Either[ApiError, NormalizedLink] =
    result:
      NormalizedLink(
        bounded(request.label, 80, "Account label is required.",
                "Account label must be at most 80 characters.").?,
        bounded(request.username, 254, "Luxmed username is required.",
                "Luxmed username must be at most 254 characters.").?,
        Secret(request.password)
      )
```

Three wins: the two near-identical validation ladders collapse into one `bounded`; the password is
wrapped in `Secret` at the earliest possible point rather than at the `forLink` call; and
`normalized.label` cannot be confused with `request.label` again. This is the wrapper AGENTS.md
permits — it enforces a real invariant (trimmed, non-empty, bounded, redacted) rather than wrapping
a primitive for its own sake.

### G8 — Make the enum mapping total and single-sourced

R4 and R6 are the same tip: one exhaustive `match` in the companion, and a `fromWire` that returns
`Either` rather than throwing.

```scala
object AccountStatus:
  extension (status: AccountStatus)
    def wireName: String = status match
      case Active     => "active"
      case AuthFailed => "auth_failed"
      case Disabled   => "disabled"

  def fromWire(value: String): Either[String, AccountStatus] =
    values.find(_.wireName == value).toRight(s"unknown account status: $value")
```

Return `Either[String, …]`, not `Either[ApiError, …]`: the repository layer, the codec and the HTTP
layer each want a different error, and `.left.map` at the call site is one word. The exhaustive
`match` (rather than a `Map`) is what makes the compiler tell you about the next case you add —
which is the whole reason the vocabulary belongs in one place.

### G9 — One clock, one type

`AccountService` takes `now: () => OffsetDateTime` (Warsaw-zoned) while `AccountClientFactory` takes
`now: () => Instant`, and `toView` immediately calls `.toInstant` anyway. Two clocks in one flow that
must agree, kept in step only by both tests fixing them to the same moment — a latent trap. Prefer a
single `now: () => Instant` threaded through both, and derive Warsaw-local values only where a
*calendar* question is actually being asked (Plan 5's day-of-week matching). An `Instant` cannot be
accidentally used as local time; an `OffsetDateTime` can.

Keep injecting these as parameters rather than reaching for `Instant.now()` inline — that part is
already right, and it is what makes the whole service testable without a clock abstraction.

### G10 — Where the helpers live

`backend/src/main/scala/lmbot/backend/support/result.scala` and `.../support/attempt.scala` — next to
the other cross-cutting support code, not in `db` or `account`. `scala.util.boundary` is plain
stdlib, so if the frontend later wants `?` over `Either`, `result` can move to `shared` unchanged and
compile on Scala.js too; `attempt` is JVM-boundary-specific and should stay in `backend`.

## R1 — Tapir schemas advertise values the wire never carries

**Where:** `shared/src/main/scala/lmbot/shared/api/Codecs.scala:158-161`

```scala
given Schema[AccountStatus] = Schema.derivedEnumeration[AccountStatus].defaultStringBased
given Schema[MonitorState]  = Schema.derivedEnumeration[MonitorState].defaultStringBased
```

`defaultStringBased` encodes the validator's possible values with `toString`, so the generated
OpenAPI and the `Validator.Enumeration` claim `"Active"`, `"AuthFailed"`, `"Disabled"` — while the
hand-written codecs 100 lines above (`Codecs.scala:54-88`) write `"active"`, `"auth_failed"`,
`"disabled"`. Tapir's documented escape hatch for this is the `encode` argument; `defaultStringBased`
is only correct when the codec also uses case names, which is why `Role` (`Codecs.scala:148`) is fine
and these two are not.

**Why it matters.** AGENTS.md, "API contract rules": *"Pin wire formats in tests; round-tripping is
not enough. A discriminated object round-trips perfectly while the Tapir `Schema` advertises a
string. `Role` shipped exactly that mismatch through 92 passing tests."* This is that failure one
level down — same class, same blind spot. Nothing breaks while Scala is the only consumer, because
both sides share the codec; the *declared* contract is simply a lie, which defeats the point of
§5.1's single shared definition. `CodecRoundTripTest` pins the JSON bytes (`AccountStatus serialises
as snake_case strings`) but never inspects the schema, so the mismatch is invisible to the suite.

**Fix.** Derive both schemas from the same source of truth as the codecs (see **R4** for
`wireName`):

```scala
given Schema[AccountStatus] =
  Schema.derivedEnumeration[AccountStatus](
    encode = Some((status: AccountStatus) => status.wireName)
  )

given Schema[MonitorState] =
  Schema.derivedEnumeration[MonitorState](
    encode = Some((state: MonitorState) => state.wireName)
  )
```

`apply`'s other parameters default to `SchemaType.SString` and `None`, so this stays string-based.

**And pin it**, in `CodecRoundTripTest`, next to the existing byte-level assertions:

```scala
private def advertisedValues[A](schema: Schema[A]): List[String] =
  schema.validator match
    case Validator.Enumeration(possibleValues, Some(encode), _) =>
      possibleValues.flatMap(encode(_)).map(_.toString)
    case other =>
      fail(s"expected an enumeration validator, got $other")

test("AccountStatus schema advertises exactly the values the codec writes"):
  assertEquals(
    advertisedValues(summon[Schema[AccountStatus]]),
    List("active", "auth_failed", "disabled")
  )
```

(`Validator.Enumeration.encode` is `Option[T => Option[Any]]`, hence the `flatMap`.) Add the
`MonitorState` twin. Without an assertion like this the next enum repeats the mistake.

## R2 — A duplicate label costs a real Luxmed password grant

**Where:** `backend/.../account/AccountService.scala:38-53`, pinned by
`backend/src/test/scala/lmbot/backend/AccountServiceTest.scala:231-246`

The flow authenticates against Luxmed *first*, then checks
`accounts.listOwned(ownerId).exists(_.label == normalized.label)`. The label check needs no network
at all, and `reserveId()` also runs before the login, burning a sequence value on every failed
attempt.

**Why it matters.** Plan 4's own invariant list (line 41): *"Linking performs at most one password
grant. Excessive login attempts can lock a Luxmed account for about a day."* AGENTS.md repeats it:
treat a sudden auth failure as a possible lock. A user who retries a link with an
already-used label spends one real login per attempt on a request that cannot succeed. The plan's
step-4 flow does not ask for this pre-check at all — it relies on the unique constraint at insert
time, which the code already handles (`23505` → `Conflict`), so the pre-check is pure surplus in its
current position.

**Fix.** Hoist it above the login and collapse the nested `try`:

```scala
def link(ownerId: Long, request: LinkAccountRequest)(using Async): Either[ApiError, AccountView] =
  validate(request).flatMap: normalized =>
    try
      if accounts.listOwned(ownerId).exists(_.label == normalized.label) then
        Left(ApiError.Conflict(duplicateLabel))
      else
        val id = accounts.reserveId()
        val deviceUuid = uuidGenerator()
        clients
          .forLink(normalized.username, Secret(normalized.password), deviceUuid)
          .authenticate() match
          case Left(error)    => Left(linkError(error))
          case Right(session) => toView(accounts.insert(row(ownerId, id, deviceUuid, session, normalized)))
    catch
      case error: Exception if hasSqlState(error, "23505") => Left(ApiError.Conflict(duplicateLabel))
      case _: Exception => Left(ApiError.Unexpected("The Luxmed account could not be linked."))
```

The `23505` handler stays — it is what makes the concurrent case safe, and the pre-check is only a
courtesy that saves a login. Extract `duplicateLabel` as a `private val` while you are there; the
message is currently spelled out three times.

**Test change required.** `AccountServiceTest:231` must drop its `enqueueAuth(server)` and assert
`passwordGrantCount(server) == 0` / `server.requests == Nil`. Rename it to something like
`duplicate label returns conflict without contacting Luxmed` — the current name pins the behaviour
we are removing.

## R3 — `AccountService.delete` has no error boundary

**Where:** `backend/.../account/AccountService.scala:136-138`

```scala
def delete(ownerId: Long, accountId: AccountId): Either[ApiError, Unit] =
  if accounts.deleteOwned(accountId, ownerId) then Right(())
  else Left(ApiError.NotFound)
```

`link` and `list` both map repository failures to `ApiError`; `delete` calls into Magnum bare, so a
DB failure leaves this method as a thrown `SQLException` instead of a value. Spec §5.7.2: errors are
values, exceptions mean bugs. The resolved review thread *"Convert repository failures to `ApiError`
at both `Either` boundaries"* applied this treatment to the other two — this looks like a missed
third site, not a decision.

**Fix.** Not a bare `catch case _: Exception` — that reintroduces exactly the hazard **G3**/**G4.1**
below warn about (it would swallow `boundary.Break` and `InterruptedException` too). Use the
`attempt.either` helper from **G3** instead, which excludes both by construction:

```scala
def delete(ownerId: Long, accountId: AccountId): Either[ApiError, Unit] =
  attempt.either(_ => ApiError.Unexpected("The Luxmed account could not be deleted.")):
    if accounts.deleteOwned(accountId, ownerId) then Right(())
    else Left(ApiError.NotFound)
```

`AccountRepo` is a non-final class, so this is testable without new seams:

```scala
val failing = new AccountRepo(xa):
  override def deleteOwned(id: AccountId, ownerUserId: Long): Boolean =
    throw SQLException("connection reset")
```

## R4 — The status/state vocabulary exists in four places

**Where:**

- `backend/src/main/resources/db/migration/V2__accounts_monitors.sql:12,43` — `check` constraints
- `shared/.../api/Codecs.scala:54-88` — JSON codecs
- `backend/.../account/AccountService.scala:86,166-171` — the literal `"active"` on insert and the
  status parser in `toView`
- `backend/.../db/MonitorRepo.scala:81-99` — `expectedStates: List[String]`, `newState: String`

Four hand-maintained copies of one wire vocabulary, and a repository API in which invalid states are
representable. AGENTS.md: *"Model alternatives and state transitions with enums, sealed ADTs, opaque
types, and exhaustive pattern matching. Make invalid states unrepresentable."*

**Fix.** One mapping in `shared`, consumed everywhere:

```scala
enum AccountStatus:
  case Active, AuthFailed, Disabled

object AccountStatus:
  extension (status: AccountStatus)
    def wireName: String = status match
      case Active     => "active"
      case AuthFailed => "auth_failed"
      case Disabled   => "disabled"

  def fromWire(value: String): Either[String, AccountStatus] =
    values.find(_.wireName == value).toRight(s"unknown account status: $value")
```

- `MonitorRepo.transitionOwned(expectedStates: List[MonitorState], newState: MonitorState)` maps to

  cross-compiled module); only the *method signatures* need the enum.

The migration's `check` constraints remain the fourth copy by necessity — worth a comment pointing at
the enum so the two are edited together.

## R7 — Coverage gaps to close before routes land

The crypto and CAS suites are genuinely strong (AAD mismatch on all three context fields, tampering,
version/format errors, stale-token CAS, restart, deterministic two-thread race, secret-free
ciphertext in three suites). Four gaps stand out:

1. **Session-store owner scoping is untested.** Every case in `PostgresSessionStoreTest` uses a single
   owner, so the `and owner_user_id = $ownerId` predicate in `load`/`replace`/`clear`
   (`PostgresSessionStore.scala:71,91,128`) — a security invariant, and one Plan 4 calls out ("every
   resource operation is scoped to the authenticated owner") — has no test at all.
   `AccountRepoTest` and `MonitorRepoTest` both cover cross-owner isolation; this store should match:

   ```scala
   test("a store scoped to another owner cannot read, replace, or clear the session"):
     val firstOwner = owner()
     val accountId = account(firstOwner)
     val intruder = owner()
     assertEquals(store(firstOwner, accountId).replace(None, session("refresh-1")), Right(()))

     assertEquals(store(intruder, accountId).load(), Right(None))
     assertEquals(
       store(intruder, accountId).replace(Some(Secret("refresh-1")), session("refresh-2")),
       Left(SessionStoreError.ConcurrentModification)
     )
     assert(store(intruder, accountId).clear().isLeft)
     assertEquals(store(firstOwner, accountId).load(), Right(Some(session("refresh-1"))))
   ```

2. **No test for an undecryptable stored session** → `Unavailable`
   (`PostgresSessionStore.scala:98`). Write garbage into `encrypted_session` (or a ciphertext bound to
   a different purpose) and assert `load()` and `replace()` both report
   `SessionStoreError.Unavailable`, and that the failure never leaks the ciphertext.

3. **`AccountRepo.updateSessionCas` is dead code** (`AccountRepo.scala:50-64`): no caller in `main`,
   no test. `PostgresSessionStore` runs its own ciphertext CAS, so this method looks superseded.
   Delete it, or wire and test it — an untested CAS helper is worse than no helper.

4. **`DbCodecsTest` has exactly one case.** `parseArrayText` is the *actual* read path under memgres
   (the default backend) whenever `rs.getArray` throws, yet only escaped backslashes are covered. I
   traced quoted commas and empty-string elements by hand and they are correct, but real Luxmed
   facility names contain commas, so pin it through the repo:

   ```scala
   test("facility names containing commas and quotes round-trip"):
     // e.g. List("Warszawa, Puławska 455", "Kraków \"Centrum\"")
   ```

   `{NULL}` elements decode to the literal string `"NULL"`. Unreachable today (the app never writes
   element nulls), worth one comment in `DbCodecs` rather than code.

## R8 — `SessionCodec.encode`'s reverse cookie sort is fragile magic

**Where:** `backend/.../luxmed/SessionCodec.scala:40-43`

```scala
cookies = session.cookies.toList
  .sortBy(_._1)(using Ordering.String.reverse)
  .map((name, value) => name -> value.value)
  .toMap
```

Sorting into a `Map` normally does nothing. It produces the pinned JSON
(`{"WAF":"abc","SESSION":"def"}` in `SessionCodecTest:22-27`) only because Scala's ≤4-element
`Map2`/`Map3`/`Map4` preserve insertion order. At five cookies the result becomes a `HashMap` and the
encoded order is arbitrary — so the suite's "pins the persisted session JSON format" guarantee
quietly stops holding exactly when a real WAF adds another cookie. Nothing breaks functionally
(decode is order-insensitive), but the test is a trap and the sort direction is unexplained.

**Preferred fix** — make the order real, not incidental:

```scala
final private case class PersistedCookieV1(name: String, value: String)

final private case class PersistedSessionV1(
    version: Int,
    /* … */
    cookies: List[PersistedCookieV1]
)

// encode
cookies = session.cookies.toList.sortBy(_._1).map((name, value) => PersistedCookieV1(name, value.value))
```

This changes the `v1` payload shape. That is free today: the migration is new, nothing in production
holds an `encrypted_session`, and a dev row that fails to decode surfaces as
`SessionStoreError.Unavailable` → re-authentication, not data loss. Update the pinned JSON in
`SessionCodecTest` and add a five-cookie case so the determinism claim is actually tested.

**Minimal alternative** if you would rather not touch the shape: sort *ascending*, keep the `Map`,
and add a comment stating plainly that ordering relies on small-`Map` insertion order and is
cosmetic — then do not pin the byte string for more than four cookies.

## R12 — `parsedMasterKey.get` depends on an invariant three screens away

**Where:** `backend/.../config/Config.scala:104`

The `.get` is unreachable only because a failed parse appends to `errors`, and `errors.nonEmpty`
returns `Left` before the `Config` is built. That is correct today and consistent with the existing

  val config = result:                 // the `.?`s cannot fail: `built` is empty

## R15 — `load()` cannot distinguish a missing account from a missing session

**✅ Fixed** — `load()` now selects the row and branches on `None`/`Some(None)`/`Some(Some(_))`,

**Where:** `backend/.../luxmed/PostgresSessionStore.scala:67-77`

  case Some(Some(value))   => decodeStored(value).map(Some(_))

Pairs naturally with the owner-scoping test in **R7**, which is where the distinction becomes
observable. Note the current `.headOption.flatten` is exactly what erases it.
