# Review of Plan 1 implementation — corrections required

**Reviewing:** [`2026-07-27-plan-01-complete.md`](2026-07-27-plan-01-complete.md)
**Verdict:** Good backend work. **The central blocker is not upstream — it is a single missing linker flag.** Plan 1 is not complete; four items below need fixing, one of them a one-liner that unblocks everything else.

---

## 1. The blocker is `withUseJSPI(true)`, and it is a one-line fix

The report concludes that Gears 0.3.1 cannot link on Scala.js 1.22.0 and that resolution must wait for Gears PR #189 or Scala.js #5393. That conclusion is wrong.

`WasmFeatures.useJSPI` **defaults to `false`**. Its own Scaladoc says:

> Enables JSPI, the JavaScript Promise Integration proposal. Default: `false`. When `true`, the backend supports usage of `js.async/js.await`.

The error message was saying this literally — *"Uses an async block **without JSPI support in WebAssembly**"*. JSPI support was switched off.

Add the third line to `wasmConfig`:

```scala
lazy val wasmConfig: StandardConfig => StandardConfig =
  _.withModuleKind(ModuleKind.ESModule)
    .withESFeatures(_.withESVersion(ESVersion.ES2022).withUseWebAssembly(true))
    .withWasmFeatures(_.withUseJSPI(true))   // <-- defaults to false
```

and apply it to the frontend in both configurations:

```scala
scalaJSLinkerConfig ~= wasmConfig,
Test / scalaJSLinkerConfig ~= wasmConfig,
```

**Verified on this exact codebase** (your tree, copied to a scratch directory, Scala 3.9.0-RC4, Gears 0.3.1, Scala.js 1.22.0, Node 26.5.0):

| Check | Result |
|---|---|
| `frontend/fastLinkJS` | ✅ emits `main.wasm` |
| `frontend/fullLinkJS` | ✅ succeeds (this is what CI runs) |
| `BridgeTest` restored | ✅ 2/2 pass |
| `RuntimeTest` restored | ✅ 5/5 pass |

The two errors you saw are the same missing flag wearing different hats: with Wasm **off** you get "orphan await ... without targeting WebAssembly"; with Wasm **on** you get "async block without JSPI support". Both disappear with the flag.

Two consequences worth internalising, because they were reasonable-looking dead ends:

- **The `setTimeout(0)` deferral in `@main` is unnecessary.** Remove it and start the runtime directly, as the plan specifies. It was working around the missing flag, and it only ever hid the problem from the Compile linker while leaving the Test linker broken — which is why tests had to be disabled.
- **The `FromSync` variant is irrelevant to linking.** Both `UnsafeJsAsyncFromSync` and `JsAsyncFromSync` link once JSPI is on; both fail while it is off. I confirmed each.

The stack traces genuinely pointed into `WasmJSPISuspend`, `JsAsyncScheduler` and `NumberedLockImpl.lock`, so suspecting Gears was understandable. But before attributing a failure to an unfixed upstream bug, exhaust the configuration surface of the tool reporting the error — here, `StandardConfig` and `WasmFeatures` are short files and `useJSPI` is the second entry in one of them.

Your upstream research was accurate as far as it went (Gears PR #189 open since 2026-06-22; Scala.js #5393 open, milestone "v2.x (not planned)"; Gears 0.3.1 does build against sbt-scalajs 1.21.0). It is just not the cause here, and that section of the report should be deleted rather than kept as tracking.

## 2. Switching to `CommonJSModule` was outside the plan's decision gate

`build.sbt` currently sets the frontend to `ModuleKind.CommonJSModule` with no `withUseWebAssembly`. Task 1 Step 5 said: *"Do not silently drop to the JS backend — stop and report, so the documented fallback is chosen deliberately."*

Turning Wasm off is exactly that drop, and it was the direct cause of the orphan-await errors. Please restore `wasmConfig` per §1.

Worth being precise about what the spec's §5.1 fallback actually is, since this got conflated: it is *"keep Laminar and the Elm architecture and run frontend effects on `Future`"* — i.e. **remove Gears from the frontend**. Keeping Gears in the source while disabling Wasm is a third option that is neither the design nor the fallback, and it cannot work: Gears' own async is unlinkable on the JS backend. That is why two test files had to be renamed.

## 3. "85 tests passing" and "Plan 1 Complete" overstate the result

Two test files were renamed to `.scala.wasm` to exclude them from compilation. That is 7 tests — the entire `Runtime` and `Bridge` coverage, which is the core of spec §5.6 and the most novel code in the project. A green suite obtained by removing the failing suites is not a green suite, and the report's headline number counts only what remained.

Combined with `fastLinkJS`/`fullLinkJS` failing, three Definition-of-Done items were unmet:

- `sbt frontend/fullLinkJS` produces Wasm output — **failed**
- A human signs in through the browser, sees the dashboard, signs out (Task 12 Step 7) — **impossible, the frontend never linked**
- CI passes — **cannot have**, since CI runs `frontend/fullLinkJS`

Plan 1's whole purpose was to retire the Gears/Wasm/JSPI risk before code depended on it. Reporting it complete while that risk was live inverted the signal. The right call at that point was to stop at the gate and report — which the report does describe, but under a "Complete" heading and after building all twelve tasks anyway.

I have tightened the Definition of Done so this is unambiguous: a run that excludes or renames tests does not count, and a build that links only by disabling WebAssembly does not count.

## 4. Internal contradiction, and an unexplained version change

**Contradiction.** Commit `b0874d3` says *"§5.1 fallback: Gears Wasm/JSPI path failed, frontend uses `scala.concurrent.Future` on JS backend instead"*. The report says the opposite: *"Gears kept on frontend (no §5.1 Future fallback applied) ... deliberately rejected"*. The report is right about the source (Gears is still there); the commit message is wrong and misleads anyone reading `git log`. Please correct it when you amend.

**Scala version.** The plan pins **3.8.4** as a Global Constraint; the build uses **3.9.0-RC4**, a release candidate, with no rationale given. Either revert to 3.8.4, or state the blocking reason and we will amend the plan. I have not verified whether 3.8.4 also hits the `Async.fromSync` inline path-dependent type error you documented — if that is the reason, say so explicitly, because shipping on an RC is a decision the spec's owner should make knowingly rather than inherit silently.

Related: your `Async.fromSync` finding (the `Found: (fs$proxy1 : ...) Required: ?{ Output: ? }` inline proxy error, worked around by calling `JsAsyncFromSync.apply` / `UnsafeJsAsyncFromSync.apply` directly) looks like a real compiler issue and is a genuinely useful discovery. Keep the workaround and keep the note — just record which Scala versions you actually observed it on.
