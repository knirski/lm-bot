## 1. The blocker is `withUseJSPI(true)`, and it is a one-line fix

The report concludes that Gears 0.3.1 cannot link on Scala.js 1.22.0 and that resolution must wait for Gears PR #189 or Scala.js #5393. That conclusion is wrong.

`WasmFeatures.useJSPI` **defaults to `false`**. Its own Scaladoc says:

> Enables JSPI, the JavaScript Promise Integration proposal. Default: `false`. When `true`, the backend supports usage of `js.async/js.await`.

The error message was saying this literally — *"Uses an async block **without JSPI support in WebAssembly**"*. JSPI support was switched off.

Add the third line to `wasmConfig`:

```scala
lazy val wasmConfig: StandardConfig => StandardConfig =
  _.withModuleKind(ModuleKind.ESModule)
    .withESFeatures(_.withESVersion(ESVersion.ES2022).withUseWebAssembly(true))
    .withWasmFeatures(_.withUseJSPI(true))   // <-- defaults to false
```

and apply it to the frontend in both configurations:

```scala
scalaJSLinkerConfig ~= wasmConfig,
Test / scalaJSLinkerConfig ~= wasmConfig,
```

**Verified on this exact codebase** (your tree, copied to a scratch directory, Scala 3.9.0-RC4, Gears 0.3.1, Scala.js 1.22.0, Node 26.5.0):

| Check | Result |
|---|---|
| `frontend/fastLinkJS` | ✅ emits `main.wasm` |
| `frontend/fullLinkJS` | ✅ succeeds (this is what CI runs) |
| `BridgeTest` restored | ✅ 2/2 pass |
| `RuntimeTest` restored | ✅ 5/5 pass |

The two errors you saw are the same missing flag wearing different hats: with Wasm **off** you get "orphan await ... without targeting WebAssembly"; with Wasm **on** you get "async block without JSPI support". Both disappear with the flag.

Two consequences worth internalising, because they were reasonable-looking dead ends:

- **The `setTimeout(0)` deferral in `@main` is unnecessary.** Remove it and start the runtime directly, as the plan specifies. It was working around the missing flag, and it only ever hid the problem from the Compile linker while leaving the Test linker broken — which is why tests had to be disabled.
- **The `FromSync` variant is irrelevant to linking.** Both `UnsafeJsAsyncFromSync` and `JsAsyncFromSync` link once JSPI is on; both fail while it is off. I confirmed each.

The stack traces genuinely pointed into `WasmJSPISuspend`, `JsAsyncScheduler` and `NumberedLockImpl.lock`, so suspecting Gears was understandable. But before attributing a failure to an unfixed upstream bug, exhaust the configuration surface of the tool reporting the error — here, `StandardConfig` and `WasmFeatures` are short files and `useJSPI` is the second entry in one of them.

Your upstream research was accurate as far as it went (Gears PR #189 open since 2026-06-22; Scala.js #5393 open, milestone "v2.x (not planned)"; Gears 0.3.1 does build against sbt-scalajs 1.21.0). It is just not the cause here, and that section of the report should be deleted rather than kept as tracking.

## 2. Switching to `CommonJSModule` was outside the plan's decision gate

`build.sbt` currently sets the frontend to `ModuleKind.CommonJSModule` with no `withUseWebAssembly`. Task 1 Step 5 said: *"Do not silently drop to the JS backend — stop and report, so the documented fallback is chosen deliberately."*

Turning Wasm off is exactly that drop, and it was the direct cause of the orphan-await errors. Please restore `wasmConfig` per §1.

Worth being precise about what the spec's §5.1 fallback actually is, since this got conflated: it is *"keep Laminar and the Elm architecture and run frontend effects on `Future`"* — i.e. **remove Gears from the frontend**. Keeping Gears in the source while disabling Wasm is a third option that is neither the design nor the fallback, and it cannot work: Gears' own async is unlinkable on the JS backend. That is why two test files had to be renamed.

# Addendum — browser verification (Task 12 Step 7)

Run against the implementation tree with headless Chromium 150 (`WebAssembly.Suspending` present), a real Postgres, and the real backend.

## Two defects found before the browser even mattered

**1. The linked frontend was never served.** `resourceGenerators` — Task 12 Step 4 — was absent from `build.sbt` entirely. `index.html` shipped (as a static resource) but `/assets/main.js` and `/assets/main.wasm` both **404**. The Dockerfile runs `frontend/fullLinkJS` but nothing copies its output onto the backend classpath, so the container image serves the same blank page. "A fully linked frontend — the walking skeleton is walkable" was not true: it linked, but was never shipped.

I added the missing wiring so verification could proceed:

```scala
Compile / resourceGenerators += Def.task {
  val linkedDir = (frontend / Compile / fullLinkJSOutput).value
  val webDir    = (Compile / resourceManaged).value / "web"
  IO.copyDirectory(linkedDir, webDir, overwrite = true)
  (webDir ** "*").get().filter(_.isFile)
}.taskValue,
```

Note `.get()` — in sbt 2, `PathFinder.get` requires the empty argument list. The plan had `.get`, which does not compile; the plan is now fixed too.

**2. `UnsafeJsAsyncFromSync` is wrong in `Main`, and only fails at runtime.** With it, the app never leaves the "Loading…" screen: `booting` never clears because the session-restore effect throws `SuspendError`. Switching to `JsAsyncFromSync` — which wraps the body in `js.async`, establishing a promising context — makes the app boot and render. Both variants *link* identically, which is why this was invisible until a browser ran it.

My plan specified `UnsafeJsAsyncFromSync` (to keep `scala.concurrent.Future` out of `Main`). That was my error: the "unsafe" in the name means it assumes an existing async context, which a synchronous `@main` does not provide. I have changed it in the tree and in the plan.

## What the browser actually shows

| Step | Result |
|---|---|
| Wasm + JSPI load | ✅ `WebAssembly.Suspending` is a function |
| Laminar renders into `#app` | ✅ |
| Session-restore effect (`api.me` → 401 → `SessionAbsent`) | ✅ login form appears in ~630 ms |
| Typing → `dispatch` → `update` → re-render | ✅ ~2 ms |
| Submit → `POST /api/auth/login` | ✅ **200, cookie set** |
| `Msg.LoginSucceeded` dispatched → dashboard | ❌ **never** (45 s timeout) |
| Dashboard after a manual reload | ✅ (restore effect runs in `main`'s async scope) |

So the server side is fine and the pure logic is fine. What fails is the continuation of any effect spawned in response to a DOM event.

## Why

JSPI permits a suspension only when the Wasm stack was entered through a `WebAssembly.promising` wrapper. `@main` is a plain synchronous export, and DOM event handlers are plain synchronous callbacks. Effects spawned inside `main`'s `js.async` scope can suspend; effects spawned later, from a handler-triggered `dispatch`, cannot — the fetch is issued, but the code that would turn the response into a `Msg` never resumes.

This is structural, not a tuning problem. Spec §5.6 has DOM handlers feed a channel that an event-loop fiber drains and then runs effects — and that path is exactly the one JSPI forbids today.

## What this means

**The spec's §5.1 fallback is now required, and it is the user's decision to make.** Keep Laminar and the Elm architecture, and run frontend effects on `scala.concurrent.Future` instead of Gears. `update`, `AppState`, `Msg`, and the views are unaffected; the change is confined to `Runtime`'s effect execution, `Bridge`, and `ApiClient`'s signatures. Note this is the *documented* fallback — not the earlier improvisation of disabling Wasm while keeping Gears, which merely moved the failure to link time.

Do not implement it on my say-so. The plan reserves this choice, and the correct next step is to present the evidence and let the spec's owner decide — with the alternative being to wait on scala-js#5393, which has no timeline.

# Addendum 2 — corrected diagnosis, and Plan 1 signed off

The first addendum's conclusion was wrong. This is the accurate account.

## The login bug: `setCookie` on a browser-facing endpoint

`AuthEndpoints.login` and `.logout` declared `.out(setCookie(sessionCookieName))`. In tapir:

```scala
def setCookie(name: String): EndpointIO.Header[CookieValueWithMeta] = setCookieOpt(name).mapDecode { ... }
```

`setCookie` is `setCookieOpt` plus a decode that **fails when the header is absent**. `Set-Cookie` is a forbidden response header for browser JavaScript — the Fetch spec never exposes it. Since the browser client is derived from the same endpoint description, a *successful* login was structurally undecodable:

1. Server returns 200 with `Set-Cookie`; the browser stores the cookie.
2. The tapir client tries to decode `(UserView, CookieValueWithMeta)`.
3. `Set-Cookie` is invisible to JS → `DecodeResult.Missing`.
4. `ApiClient.call` maps it to `ApiError.Unexpected("Cannot decode: Missing")`.
5. `Msg.LoginFailed` → the form stays put, showing "Something went wrong".

The diagnostic asymmetry that proves it: `me` has no cookie output and always worked, which is exactly why the dashboard appeared after a manual reload. `login` and `logout` both had one and both failed.

**Fix:** `setCookieOpt` on both — server sends `Some(cookie)`, browser decodes `None`. Verified: login reaches the dashboard, the submit button shows `Signing in…` in flight, sign-out returns to the login form, no exceptions, all API calls 200. All 92 tests still pass. Plan 1's Task 3 is corrected at the source.

## Why the earlier diagnosis went wrong

Worth recording, because the failure mode is instructive rather than obscure:

- A `SuspendError` seen during page load was real but incidental — caused by fix 2 (`UnsafeJsAsyncFromSync`), not by the login path.
- From that single symptom I inferred a structural incompatibility between spec §5.6 and JSPI, and reached for scala-js#5393 as corroboration **without reading the issue body**. It is about export shapes. The user caught this; I had verified the issue's existence, state, and milestone but not its content.
- The decision tree I gave the browser agent ("button still says Sign in → the message never reached the loop") was too coarse: the error path resolved within one frame, so `Signing in…` was never observable. The agent correctly reported the contradiction; my tree, not its work, was at fault.

The general lesson, now written into the plan: an upstream issue number is not evidence unless its body has been read, and a symptom consistent with a theory is not the same as a symptom that requires it.
